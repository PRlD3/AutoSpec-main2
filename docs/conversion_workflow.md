# MBPP 到 C 的可验证转换工作流

## 研究目标

目标不是把 Python 的表面语法逐句替换成 C，而是在明确输入约束、数据表示和测试语义后，构造一个可编译、可执行、可验证的 C 程序。转换结果需要同时满足三层要求：语法可编译、测试行为一致、形式化验证目标没有因为翻译而改变。

## 核心原则

### 语义先于语法

Python 的列表、元组、集合、字符串、动态整数和异常行为没有天然的一一对应 C 类型。每种 Python 类型都必须先选择 C 表示，再定义操作语义。例如列表应表示为 `{data, length, capacity}`，字符串应表示为以 `\0` 结尾的字符数组并明确容量，集合交集应转换为确定的数组算法，而不是强行映射到标量表达式。

### 约束先于生成

每个 MBPP 条目先提取函数签名、输入类型、输出类型、测试输入范围、边界条件和副作用，再决定是否进入某个转换子集。无法确定类型或存在未建模语义时，应该标记为“不可安全转换”，而不是生成看似合理但语义不可信的 C 代码。

### 测试不是充分证明

MBPP 测试只能证明有限样例上的行为一致。转换正确性应采用分层证据：Python 原程序测试、C 测试、随机或性质测试、编译器检查，以及 Frama-C/WP 对 C 代码的形式化验证。通过 AutoSpec 只能说明 C 版本在给定规格和模型下可验证，不能单独证明 Python-C 等价。

## 推荐流程

1. 数据清洗：解析 MBPP 对象格式，统一 `key`、函数代码、测试列表和解答字段，去除重复条目，记录缺失字段。
2. 语法分析：使用 Python AST 提取函数、表达式、语句、导入和调用，不使用正则表达式直接改写代码。
3. 类型与契约推断：结合函数签名、测试样例和代码使用方式推断整数、浮点数、布尔值、序列和字符串，并生成前置条件、后置条件和定义域约束。
4. 选择转换子集：按语言特性分层，先处理整数标量、条件、循环、简单数组和返回值，再扩展字符串、二维数组、集合和排序等库语义。
5. 中间表示：将 Python AST 降低为带类型的内部表示，显式记录变量类型、容器长度、所有权、可能的异常和循环不变量。
6. C 代码生成：从内部表示生成函数、辅助数据结构、边界检查、测试驱动程序和 ACSL 注释。生成代码与测试代码分离，便于复核。
7. 编译与动态一致性：使用 GCC 或 Clang 编译 C harness，运行原 Python 测试和 C 测试；对可生成的输入进行差分测试，失败时优先判定为翻译损失。
8. 形式化验证：在独立输出目录运行 Frama-C/WP 和 AutoSpec，保存命令、版本、模型、超时、标准输出和标准错误。
9. 失败分类：区分解析失败、类型推断失败、表示不足、代码生成失败、Python-C 行为不一致、C 编译失败、规格不足、证明器失败和工具环境失败。
10. 统计与抽样复核：报告各阶段分母，给出转换成功率、差分测试通过率、AutoSpec 通过率、工具失败率和典型案例；对自动判定结果进行人工抽样。

## 有效转换的判定

一个条目只有在以下证据都成立时才进入“有效转换”集合：

- Python 源代码和测试可解析；
- 输入输出表示和边界条件有明确记录；
- C 代码可在固定编译器和标准下编译；
- C harness 与 Python 测试在相同输入上得到等价结果；
- 关键边界和随机样本的差分测试通过；
- C 端未引入未定义行为、越界、整数溢出或未处理的空指针路径；
- AutoSpec/Frama-C 的验证结果可复现，并能追溯到具体输入、版本和配置。

若只完成编译，标记为“可编译”；若只通过固定测试，标记为“样例一致”；若缺少语义证明，不应写成“等价已证明”。

## 转换的关键因素

- 数据表示：容器和字符串的 C 表示决定了后续算法与规格是否可验证。
- 输入契约：长度、范围、非空、排序性和唯一性等约束决定 C 代码是否安全。
- 语义库：Python 内置函数和方法必须有经过测试的 C 运行时实现。
- 控制流：循环初始化、终止条件、变更量和不变量是 Frama-C 证明的核心。
- 测试翻译：Python 的元组、集合、浮点比较和异常断言不能机械翻译成 `assert`。
- 可追溯性：每个生成文件必须能回溯到数据集键、转换器版本、规则版本和失败原因。
- 失败分层：翻译失败与工具失败必须使用不同的分母统计，否则通过率没有研究意义。

## 论文实验设计

建议将实验拆成转换层和验证层。转换层报告语言特性覆盖率、成功率、编译率和差分一致率；验证层报告 AutoSpec 通过率、证明时间、超时率和环境失败率。设置基线：人工规则转换、LLM 直接生成、AST/IR 规则转换和规则加 LLM 修复。对每个条目保留完整中间产物和失败日志，并使用固定数据划分，避免用测试结果反向修改转换规则后仍使用同一测试集宣称泛化。

## 当前项目的下一步

先建立一个小型、可解释的转换子集和黄金样例集，再逐类扩展。每新增一种 Python 语义，必须同时新增 C 表示、转换规则、运行时辅助函数、测试样例、ACSL 约束和失败分类，不应只增加一个语法分支。
